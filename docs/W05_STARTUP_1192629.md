## Confirmed source defect

The old 300-second W05 launch deadline included PowerShell prerequisites, runtime/TLS/database checks, and a synchronous full worker verification before TCP 15002 existed. That verifier checks the source binding, executable/private DLLs and 26,748 pinned game-data files (726,207,542 bytes). There was no phase timing and failed health probes returned only `False`. This made a slow, still-validating launch indistinguishable from an unavailable listener or invalid health response.

Native encounter processes are started on demand. The READY health count describes verified worker availability/configured capacity; it does not prove that an AI battle has executed.

## Correction

- Keep all existing source, executable, DLL and game-data verification intact and before listener creation.
- Acquire the existing battle daemon lock before worker verification, preventing a second daemon from duplicating that scan.
- Record ordered runtime, worker-verification, listener and serving phases with UTC timestamps and monotonic elapsed times. A fresh per-launch diagnostic file identifies the corresponding child.
- Separate finite budgets: 300 seconds for preflight/runtime, 900 seconds for full worker verification, and 75 seconds for authenticated-listener readiness, with a 1,275-second overall cap. These are upper bounds, not expected startup times. Repeated output never renews a deadline. Network probes use the remaining deadline.
- Record elapsed time, last phase and sanitized health failures. Never include credentials or arbitrary server replies.
- Mark PASS only after the existing pinned TLS, protocol, implementation release and requested native-worker count checks succeed. READY text and phase records cannot produce PASS.

The existing optional-worker fallback can open a listener with unavailable worker capacity; W05 still refuses PASS unless the requested worker capacity is verified. The worker builder and all worker-bound client sources remain unchanged.
